Case 03 / Working prototype

Making a brittle browser task fail usefully

This was a small Python and Playwright tool for repeatable patent-result exports. The download itself was easy. The real work was making the script deal with the browser states that make simple automation unreliable.

PrototypeBrowser-based patent export automation
StackPython + Playwright
My roleDesigner / developer
Main constraintChanging UI states without silent failure
The problem

The manual step was repetitive. The interface was not stable enough for a one-selector script.

A script that only works on the happy path is a demo.

The basic flow was straightforward: open a bounded patent search, find the download control, choose CSV, wait for the browser's download event, and save the result with a predictable name.

What made the tool useful was dealing with the things around that flow: a control rendered as a button instead of a link, a consent dialog, a slow page, a download that never begins, or a CAPTCHA that requires a person.

What I wanted from the tool

Try reasonable alternatives. Verify that the expected event actually happened. If the script cannot continue, tell me what likely blocked it and what I need to do next.

The prototype

I use code when I need to test whether an interaction idea survives real state changes.

Build for variation instead of assuming one perfect selector.

download_portfolio_results.pysanitized excerpt
# The same visible control may be represented several ways.
download_selectors = [
    "text=Download",
    "a:has-text('Download')",
    "button:has-text('Download')",
    "[aria-label*='Download' i]",
]
for selector in download_selectors:
    try:
        control = page.locator(selector).first
        if control.is_visible(timeout=2000):
            control.click()
            break
    except TimeoutError:
        continue
# When automation cannot recover, give the user a useful next step.
raise RuntimeError(
    "Download timed out. Resolve any consent or CAPTCHA screen and re-run."
)
What I built in on purpose

The code is small, but it has a clear recovery path.

The script checks the result instead of assuming the click worked.

01
Wait for a usable page
Let the result page stabilize before interacting with it.
02
Handle common interruptions
Try to dismiss known consent prompts when they appear.
03
Try several valid controls
Do not bind the whole workflow to one fragile DOM representation.
04
Wait for the download event
A click is not success. The actual browser download event is the confirmation.
05
Save predictably
Use a known directory and deterministic file names so downstream work is repeatable.
06
Stop with context
If the tool cannot recover, explain the likely blocker and return control to the user.
Why this belongs here

This is a coding example, but the design issue is the same one I see in larger AI workflows.

I use code to pressure-test behavior, not just to automate clicks.

Some questions are hard to answer in a diagram. What happens when the UI changes? How long should the system wait? What counts as success? When should it retry? When should it stop and ask for help?

I have used the same mindset in larger RF and test-automation work: observe state, verify the outcome, recover where it is reasonable, and make the failure useful when it is not.

1
Alternatives are planned

The tool tries a small set of reasonable options rather than failing at the first mismatch.

2
Success is observable

The download event confirms the outcome. The click itself does not.

3
The user gets the reason

A timeout points to likely blockers instead of returning a generic failure.

4
Human intervention is allowed

Running headed during development keeps the state visible when the environment changes.

Reflection

The prototype works, but there are obvious ways I would make the recovery even better.

What I would add next.

I would capture structured logs and a screenshot on failure, add an explicit retry budget, and make resume/cancel behavior part of the user flow. That would give the person enough context to recover without rerunning the entire task blindly.

For agent-assisted products, I would apply the same rule: detect the state, try bounded recovery, verify the result, and hand control back with enough context for the person to continue.
