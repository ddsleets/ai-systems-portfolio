Case 02 / Agent rules

Writing the rules before giving an AI more authority

I had a simple concern: a fluent answer could be mistaken for a legal or technical conclusion. Before adding more tools or automation, I wrote down the assistant's job, its limits, when it had to ask, and where a professional took over.

ArtifactIP Navigator agent charter
DomainIP research assistance
My roleAI lead / workflow designer
Main constraintAssist aggressively without pretending to be the decision-maker
The problem

Fluency can make a model sound more certain than the evidence justifies.

I was less worried about the model being wrong than being wrong and sounding certain.

The assistant was meant to help an IP analyst interpret patent or trademark material, compare public product information, identify possible investigative paths, and formulate searches. Those are useful tasks, but they sit next to work where legal significance and factual verification matter.

So the first artifact was not a screen. It was a short operating charter that defined the lane before the system did any work.

The rule I kept coming back to

If the model does not have enough information to know the scope, it should ask. If it cannot verify a fact, it should say so. If the next step carries professional or legal consequence, it should hand the decision back.

The charter

I wanted the important boundaries to be readable in under a minute.

The rules were written in plain language.

IP Navigator / operating chartersanitized summary
ROLEResearch assistant for an IP analyst

Interpret technical material, compare public product information, and help develop search paths.

CAN HELP WITHClaims, specifications, product descriptions, and public searches

Structure the research, identify correlations, and suggest what to investigate next.

CANNOT CLAIMFormal legal advice or facts it has not verified

No access to non-public databases. Patent numbers, product links, and other factual details require checking.

WHEN INPUT IS UNCLEARAsk before filling in the gap

Clarify the patent, claims, market context, or other missing scope instead of inventing an assumption.

BEFORE ACTIONHuman professional review is required

The assistant can support research and recommendations. A qualified professional owns the consequential decision.

Turn rules into states

A policy is more useful when the product changes behavior because of it.

I would not hide these rules in a system prompt.

If this were a product, the user should be able to tell which mode the assistant is in without reading policy text. The state should be visible in the interaction.

A
Researching
The system is organizing information or searching inside the agreed scope. No external decision is being made.
B
Needs context
A missing detail changes the answer, so the assistant asks a focused question before continuing.
C
Needs verification
A factual claim or source cannot be confirmed. It stays marked until a person verifies it.
D
Ready for professional review
The research package is complete enough to hand off, but the consequential judgment still belongs to the human expert.
Design tension

More autonomy is not automatically better.

The useful question is: what can the system safely decide here?

I think autonomy should depend on the task. Extracting facts from a supplied document is different from recommending an investigation path, and both are different from making a legal conclusion.

That distinction changes the product. Low-risk, reversible work can move with less friction. Missing context should trigger a question. Unverified facts should stay visibly unverified. High-consequence decisions should end at a clear review point.

Less guessingAmbiguity has a defined response instead of becoming an invisible assumption.
Facts stay checkableIdentifiers, links, product correlations, and source claims are treated as things to verify.
The boundary is clearThe assistant can be useful without presenting itself as the final authority.
Reflection

The charter is useful, but a real product has to make those rules visible at the point of use.

What I would build next.

I would turn the hidden rules into visible interaction states: current objective, scope, permission level, unverified items, sources used, and the exact reason the assistant stopped. I would also make it easy for the user to narrow scope, revoke permission, or redirect the task without starting over.

That is the part of agent design I find most interesting. The model can be powerful, but the user should never have to guess what authority it thinks it has.
